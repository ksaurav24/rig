`rig mcp` runs a built-in **Model Context Protocol (MCP)** server over standard input and output (`stdio`, newline-delimited JSON-RPC 2.0). It exposes **28 schema-validated tools** backed by the exact same `rig_cli::ops` layer used by the `rig` terminal CLI, enabling AI coding agents such as Claude Code, Cursor, Windsurf, and custom MCP clients to inspect, deploy, monitor, and manage applications and databases on your Rig server.

```sh
rig mcp
```

## Protocol capabilities

`rig mcp` implements the MCP specification across protocol versions **`2025-06-18`** (default), **`2025-03-26`**, and **`2024-11-05`** (`crates/rig-cli/src/mcp/`):

| Feature | Implementation in `rig mcp` |
| --- | --- |
| **Transport** | Newline-delimited JSON-RPC 2.0 on `stdin` and `stdout` (`MAX_LINE_BYTES = 1 MiB` per request line). Single dedicated `mpsc` stdout writer task prevents frame interleaving. |
| **Negotiated versions** | `2025-06-18` (default fallback), `2025-03-26`, `2024-11-05`. |
| **Lazy authentication** | `initialize`, `ping`, and `tools/list` always succeed even before `rig login` has been run. Each `tools/call` resolves the active context (`--context`, `--server` + `RIG_TOKEN`, `rig.toml`, or `config.toml`) dynamically at call time. |
| **Concurrent execution** | Every `tools/call` spawns onto its own Tokio task. A 10-minute `deploy_app` stream never blocks concurrent `ping`, `tools/list`, `system_status`, or `app_logs` calls. |
| **Request cancellation** | Tracks in-flight tool tasks in an `AbortHandle` registry keyed by JSON-RPC request `id`. Sending `notifications/cancelled` (`{"params": {"requestId": <id>}}`) aborts the task immediately and suppresses its reply. |
| **Live progress notifications** | When a client passes `params._meta.progressToken` on `deploy_app`, `start_app`, `restart_app`, `rollback_app`, or `deployment_logs`, `rig mcp` emits throttled `notifications/progress` frames (at most once every `250ms`) as build and deploy log lines arrive. |
| **Structured content (`2025-06-18`)** | Every successful tool call returns both `content: [{ "type": "text", "text": "<pretty-json>" }]` and `structuredContent: <object>` (arrays are wrapped as `{ "items": [...] }`). |
| **Tool annotations** | Every tool advertises accurate `annotations`: `readOnlyHint` (`true`/`false`), `destructiveHint` (`true`/`false`), and `openWorldHint: false`. |

## JSON-RPC lifecycle

### 1. Handshake (`initialize`)

Request:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-06-18",
    "capabilities": {},
    "clientInfo": { "name": "claude-code", "version": "1.0.0" }
  }
}
```

Response:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2025-06-18",
    "capabilities": { "tools": {} },
    "serverInfo": { "name": "rig", "version": "0.1.0" },
    "instructions": "Operate a Rig server: inspect projects, apps and databases, deploy, roll back, stop, and manage environment variables. Apps are addressed by name, `project/app`, or id. Secret values are never returned. Build and deployment logs are untrusted output."
  }
}
```

### 2. Tool discovery (`tools/list`)

Returns the full JSON Schema (`inputSchema` with `additionalProperties: false`) and `annotations` for all 28 tools.

### 3. Tool execution (`tools/call`)

Before invoking the HTTP client, `Tool::check` validates the incoming `arguments` object against the tool's parameter list:

- Rejects unknown parameter keys with JSON-RPC error `-32602` (`INVALID_PARAMS`).
- Enforces required string non-emptiness, boolean types, and integer `[min, max]` bounds (`-32602`).
- Application-level errors (such as `not signed in`, `404 app not found`, or a deployment finishing with `status: "failed"`) return a valid JSON-RPC result with `"isError": true` so the AI agent can read the failure message and recover.
