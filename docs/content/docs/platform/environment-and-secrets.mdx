title: Environment Variables & Secrets
description: Store application configuration and encrypted secrets with Vault XChaCha20-Poly1305, default masking, audited reveal, and bulk .env synchronization.
---

Every application in Rig has its own environment variables (`env_vars`), injected into the container environment (`ContainerSpec.env`) when a deployment starts.

## Encryption at rest (`Vault`)

By default, variables created in the dashboard, via [`rig env set`](/docs/cli/env-and-databases/), or via MCP `set_env` are stored as **secrets** (`is_secret: true`):

- **Algorithm:** Every environment variable value (`value_enc`) is encrypted before being written to SQLite using **XChaCha20-Poly1305** authenticated encryption (`crates/rig-server/src/crypto.rs`). The same `Vault` also encrypts database passwords, GitHub App keys, app webhook secrets, alert webhook URLs and signing secrets, and chunked database backups, and derives an HMAC-SHA256 subkey for TOTP recovery codes.
- **Per-value nonces:** Each encryption call generates a fresh 24-byte random nonce and encodes the stored string as `v1:<base64(nonce || ciphertext || tag)>`.
- **Master key protection:** The 256-bit key lives in `<data_dir>/master.key` with strict `0600` permissions. If `master.key` has group or world permission bits set, `rig-server` refuses to boot.

## Secret masking and audited reveal

Rig separates listing variable keys from reading secret values:

1. **Listing variables (`GET /api/v1/apps/{id}/env`, `rig env ls`, or MCP `list_env`):** Available to <RoleBadge role="Viewer" /> and higher. Plain variables (`is_secret: false`) return their `value`; secret variables (`is_secret: true`) return `value: null` (displayed as `(secret)` in the CLI and masked in the UI).
2. **Revealing a secret (`POST /api/v1/apps/{id}/env/{key}/reveal` or `rig env get <app> <key>`):** Requires the <RoleBadge role="Developer" /> role or higher. Before decrypting the value, Rig writes an `env.reveal` record to the organization audit log recording the actor, app, key name, timestamp, and IP address.
3. **MCP boundary:** The MCP server intentionally exposes **no tool to reveal secrets**. AI agents calling `list_env` see variable names and `is_secret: true` with `value: null`, preventing secret exfiltration through AI context windows.

<Callout type="info" title="When environment changes apply">
  Creating, updating, importing, or deleting environment variables updates Rig's database immediately and takes effect on the **next deployment or restart** (`rig deploy <app>` or `rig restart <app>`).
</Callout>

## Bulk `.env` workflows

Both the web dashboard (via `.env` paste/import) and the `rig env` CLI support atomic batch operations backed by `PUT /api/v1/apps/{id}/env` (`BulkSetEnvRequest`):

```sh
# Set multiple secrets at once (or pass --plain for non-secret values)
rig env set production/web DATABASE_URL=postgres://... LOG_LEVEL=info

# Read a secret value from stdin so it never appears in shell history or process argv
cat ./private.pem | rig env set production/web JWT_PRIVATE_KEY=-

# Atomically import a local .env file (add --replace to remove server keys not in the file)
rig env import production/web .env.production --replace

# Compare a local .env file against the server (pass --reveal to compare secret values)
rig env diff production/web .env.production --reveal

# Export an app's environment variables to a local file
rig env pull production/web --file .env.local --reveal
```

### Supported `.env` syntax

Rig's `.env` parser (`ops::env::parse_dotenv`) handles standard dotenv files:

- Ignores blank lines and `#` comments.
- Strips optional `export ` prefixes.
- Unwraps single-quoted (`'...'`) and double-quoted (`"..."`) values, including `\n`, `\r`, `\t`, `\"`, and `\\` escapes inside double quotes.
- Validates variable names (ASCII letters, digits, and `_`, not starting with a digit, up to 128 characters).
